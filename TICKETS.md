### T-01 · P0 · Allow a session to be created directly in the Vm tier

**Plan:** §4.3 `create(tier, …)`, §4.15 `POST /v1/sessions` body `tier`.
**Gap:** `refuse_unenforced` rejects `TierPreference::Vm`
(`crates/sandbox-server/src/api.rs:716` — `matches!(config.tier_preference,
TierPreference::Auto | TierPreference::Isolate)` → `refuse("the vm tier")`), and
`create_session` has no branch that builds a `VmSession` directly
(`api.rs:1675` only handles `initial_snapshot` / `initial_template` /
`IsolateBackend`). A caller cannot ask for a VM session up front; they can only
arrive at one by promotion.
**Do:**
1. In `refuse_unenforced`, accept `TierPreference::Vm` when `state.vm.is_some()`
   (the gate already exists at `api.rs:795` `promotable`).
2. In `create_session`, add a `TierPreference::Vm` branch that takes a guest from
   `state.vm_pool` and wraps it as a `VmSession` (mirror `promote_session`,
   `api.rs:1981`), stamping `tier: Tier::Vm`.
3. Cover with a test: create with `tier: "vm"`, exec a command, assert it ran in
   the guest. (Gated `--ignored` behind `SANDBOX_VM_IMAGE` like
   `crates/sandbox-server/tests/vm_fallback.rs:51`.)
**Verify:** `cargo test -p sandbox-server --test rest` + the new gated test.

### T-03 · P0 · Make metering durable on the single-node path

**Plan:** §4.14 metering to a durable queue; §5 billing must survive restart.
**Gap:** `SessionMeter`/`MeterTable` is in-memory
  (`crates/sandbox-server/src/metering.rs:70` `Arc<Mutex<HashMap<…>>>`) and is the
  only metering source on a non-clustered build — a restart zeroes every reading.
  The durable billing stream (`crates/sandbox-server/src/billing.rs`) is gated
  `#![cfg_attr(not(feature = "clustered"), allow(dead_code))]`
  (`billing.rs:1`) and only reachable on the clustered build (`AppState::billing`
  is `None` otherwise). So on the default `deploy/` single-node deployment,
  billing is lost on restart.
**Do:**
1. Give `MeterTable` a write-behind to a durable sink (the same Postgres table
   the clustered `BillingLog` uses, or a local append file under `data_dir`) so
   `record_exec` is acknowledged only after it is persisted.
2. On startup, replay the sink to rebuild `MeterTable` before the server accepts
   requests.
3. Un-gate `billing.rs` so the single-node server appends `session.started`,
   `session.stopped`, `usage.reading` events.
4. Test: record usage, restart the store, assert `GET /v1/usage` is unchanged.
**Verify:** `cargo test -p sandbox-server --test clustered_metering` plus a new
single-node persistence test.

### T-04 · P0 · Complete the node: module shim

**Plan:** §4.5 requires the node compat shim to cover the modules an agent
actually reaches for.
**Gap:** the shim installs `fs env process buffer child_process crypto events
os path stream url util` (`crates/sandbox-runtime/src/runtime.rs:97`). Missing
modules an agent commonly imports: `assert`, `http`, `https`, `net`, `readline`,
`zlib`, `worker_threads`, `module`, `dns`, `tls`, `string_decoder`,
`querystring`. `process.cwd()` is hardcoded `"/"` and `process.env` is `{}`
(`runtime.rs:145`-`147`) — both wrong for a session that has a working dir and
env.
**Do:**
1. Add the missing `node:` modules (or an honest `SandboxError::unsupported`
   for the network ones that have no isolate backend: `http`, `https`, `net`,
   `dns`, `tls`).
2. Wire `process.cwd()` and `process.env` to the real session working dir and
   env (the VFS cwd and the `env` op already exist).
3. Add conformance tests per new module in
   `crates/sandbox-runtime/tests/`.
**Verify:** `cargo test -p sandbox-runtime`.
